| 항목 | 내용 |
| --- | --- |
| 서버 | 카페24 가상서버, vCPU 4 (Intel Xeon E3-1230 v5), RAM 2GB, Ubuntu 24.04 |

PC에서 측정한 응답 시간에는 인터넷 왕복과 SSH 터널 시간이 포함된다. 그래서 1번은 서버 안에서 잰 처리 시간(요청 기록의 `latency_ms`)도 함께 적는다.

## 1. 게이트웨이 자체 처리 시간

AI 응답 대기 0, 동시 50명이 60초 동안 쉬지 않고 요청 (`overhead.js`).

| 지표 | 결과 |
| --- | --- |
| 처리량 | **초당 1,771건** (60초 동안 106,374건) |
| 실패율 | 0% |
| 서버 안 처리 시간 (사용량 제한 + 예산 선차감·정산) | 평균 8.9ms · p50 7ms · **p95 20ms** · p99 34ms |
| PC에서 본 응답 시간 (네트워크 포함) | p50 24.9ms · p95 49.6ms · p99 73.6ms |

요청 하나에 Redis Lua 스크립트 2번(사용량, 예산), Redis 증감 1번, PostgreSQL 기록 1번이 들어가도 p95 20ms 안에 끝난다.

## 2. 느린 AI 응답에서 동시 접속: 가상 스레드 효과

AI가 2초씩 걸린다고 가정하고 동시 사용자를 30초 동안 500명까지 늘린 뒤 60초 유지 (`concurrency.js`). 가상 스레드만 켜고 끄며 같은 조건으로 비교했다.

| | 가상 스레드 ON | 가상 스레드 OFF (톰캣 기본 200 스레드) |
| --- | --- | --- |
| 처리량 | **초당 190건** | 초당 91건 |
| 응답 시간 p50 / p95 | **2.08초 / 2.19초** | 4.94초 / 5.16초 |
| 실패율 | 0% | 0% |
| 앱 메모리 / CPU (측정 중) | 479MB / 27% | 407MB / 104% |

- 가상 스레드를 끄면 요청 스레드 200개가 모두 AI 응답(2초)을 기다리며 묶인다. 최대 처리량이 초당 100건(200 ÷ 2초)으로 막히고, 나머지 요청은 줄을 서서 응답 시간이 약 5초(500명 ÷ 초당 100건)까지 늘어난다. 측정값과 계산이 맞는다.
- 가상 스레드를 켜면 기다리는 동안 OS 스레드를 놓아주므로, 500명이 동시에 기다려도 응답 시간은 AI 대기 2초 + 약 0.1~0.2초에 머문다.

## 3. 예산 정확도: 몰려도 한도를 넘지 않는가

게스트 하루 예산을 $0.01(10,000 마이크로달러)로 줄이고, 1,000건을 300명이 동시에 보냄 (`budget-burst.js`, AI 대기 200ms).

| 지표 | 결과 |
| --- | --- |
| AI 처리 | 103건 |
| 예산 소진으로 데모 응답 | 897건 |
| 실패 | 0건 |
| **실제 사용액** | **$0.00175 (한도 $0.01의 18%)** — 한도 초과 0 |

**발견한 문제:** 호출 전에 "나올 수 있는 최대 비용"(입력 상한 + `max_tokens` 1,024개, 이 조건에서 건당 약 $0.0005)을 먼저 잡아두기 때문에, 동시에 몰리면 실제로는 18%만 썼는데도 예산이 찬 것처럼 보여 897건이 데모 응답을 받았다. 비용 초과를 막는 대신 버스트 상황에서 처리량을 크게 손해 본 것.

### 3-1. 개선: 기다렸다 재시도 + 선차감액 줄이기

1. **"진짜 소진"과 "일시적으로 꽉 참" 구분**: 정산 전 선차감액 합계를 따로 기록(`budget-inflight` 키)해서, 실제로 쓴 돈만으로 한도를 넘었으면 바로 포기하고, 진행 중인 요청들의 선차감 때문에 꽉 찬 것이면 다른 요청이 정산하며 돌려주는 예산을 **최대 3초** 기다리며 다시 시도한다 (20~50ms 간격, 가상 스레드라 대기 비용이 작음). 선차감·정산은 두 키를 함께 바꾸는 Lua 스크립트로 처리.
2. **선차감액 절반으로**: 데모 답변 최대 길이 `max_tokens`를 1,024 → 512로 줄임 (실제 답변은 대부분 100~300토큰). 잘린 답변에는 안내 문구를 붙임.

같은 조건(예산 $0.01, AI 대기 200ms, 동시 300명, 1,000건)으로 로컬에서 개선 전후를 비교했다 (개선 전 수치는 서버 측정과 동일하게 재현됨).

| | 개선 전 | ① 기다렸다 재시도 | ①+② 답변 길이 512 |
| --- | --- | --- | --- |
| AI 처리 | 103건 | 442건 | **538~542건** |
| 데모 응답 | 897건 | 558건 | 419~440건 |
| 실제 사용액 / 한도 | 17.5% | 75% | **91~92%** |
| 한도 초과 | 0 | 0 | 0 |

- **대가**: 예산이 정말 바닥나기 직전에는 데모 응답을 받기까지 최대 3초를 기다릴 수 있다 (전에는 즉시 데모 응답). 대신 같은 예산으로 5배 넘는 요청이 실제 AI 답변을 받는다.
- ①+② 측정에서 실행마다 0~43건의 연결 실패가 있었는데, 응답 시간 0ms의 연결 단계 실패로 로컬 Windows에서 300개 연결이 한꺼번에 몰릴 때 생기는 현상이다 (서버 오류 없음, ① 측정에서는 0건).

## 4. 테스트 중 발견한 운영 문제: Metaspace 부족

부하 테스트 직후 운영 로그에서 `OutOfMemoryError: Metaspace`로 앱이 한 번 재시작된 기록을 발견했다 (`-XX:+ExitOnOutOfMemoryError`와 재시작 정책 덕분에 1초 만에 복구).

- 원인: Metaspace(클래스 정보 저장 영역) 한도를 128MB로 잡았는데, 실측해 보니 시작 직후 약 101MB, **실제 Claude 첫 호출 후 약 124MB**였다. Anthropic SDK가 첫 호출 때 많은 클래스를 불러온다.
- 가짜 응답 모드로 한 부하 테스트에서는 SDK 코드를 타지 않아 드러나지 않았고, 실제 모드 운영에서만 발생했다.
- 조치: 한도를 256MB로 올림 (실제 사용량은 그대로라 메모리 부담은 거의 늘지 않음)

## 다시 돌리는 법

서버에서 (root):
```bash
./stack.sh up 0ms true          # AI 대기 0, 가상 스레드 ON
./stack.sh up 2s false          # AI 대기 2초, 가상 스레드 OFF
./stack.sh up 200ms true 0.01   # 게스트 예산 $0.01
./stack.sh stats                # 메모리·CPU
./stack.sh budget               # 오늘 게스트 예산 사용액
./stack.sh down                 # 모두 지우기
```

PC에서:
```bash
ssh -N -L 8090:127.0.0.1:8090 gateway-server   # 터널 (별도 창)
k6 run -e VUS=50 -e DURATION=60s -e LABEL=vt-on overhead.js
k6 run -e PEAK=500 -e LABEL=vt-on concurrency.js
```

3번(동시 300명이 한꺼번에 새 연결)은 PC의 SSH 터널이 연결 대기열을 감당하지 못해 서버 안에서 실행했다.
