집돈 계산기

집·대출·차처럼 큰돈이 드는 계산을, 결과뿐 아니라 계산식과 법령 근거까지 보여주는 계산기 사이트. 실제 도메인에서 운영 중입니다.
2단계로 국토교통부 실거래가를 수집하는 Spring 서버를 붙여, 계약하려는 집의 전세가율(깡통전세 위험)을 보여줍니다.

PROBLEM 왜 만들었나

대출 상환액이나 중개보수는 한 번 잘못 계산하면 수십만~수백만 원이 달라집니다. 그런데 많은 계산기가 결과 숫자만 보여줍니다.

  • 근거가 없다: 어떤 공식, 어떤 반올림, 어떤 법령 기준인지 알 수 없어 은행·중개사무소 금액과 다르면 무엇이 맞는지 확인할 수 없다
  • 기준이 바뀐다: 중개보수 요율은 2021년에 개정됐고, 전월세 전환율 상한은 기준금리를 따라 움직인다
  • 서버를 더 늘리고 싶지 않다: 이미 게이트웨이가 돌고 있는 2GB 서버 한 대로 함께 운영해야 한다

공인중개사 자격을 가진 개발자로서, 계산식과 근거를 공개하고 계산 로직을 테스트로 검증하는 계산기를 만들었습니다.

FEATURES 전세 위험 확인 + 계산기 7종
  • 전세 위험 확인: 수도권 아파트·빌라를 검색하면 면적별 최근 매매·전세 중앙값, 전세가율과 위험 구간, 근거 거래를 보여주고, 내 보증금 기준 전세가율도 계산 (2단계 · Spring 서버)
  • 대출 상환: 원리금균등·원금균등·만기일시 비교, 월별 상환표
  • 전세대출 이자: 월 이자, 보증료 포함 총비용
  • 중개보수(복비): 공인중개사법 시행규칙 상한 요율·한도, 월세 거래금액 환산(×100 / ×70)
  • 전월세 전환: 주택임대차보호법 상한(기준금리 + 2%) 대비 실제 전환율 확인
  • 자동차 할부: 월 납입금, 할부 기간별 총 이자 비교
  • 적립식·거치식 투자: S&P 500·나스닥 100 최근 10년 실제 수익률 재현, 목표 금액 역산
  • DSR: 소득 대비 원리금 비율, 스트레스 금리 반영 최대 대출액
ARCHITECTURE 서버 한 대에 서비스 셋
  1. 브라우저모든 계산은 브라우저에서 실행. 입력한 금액은 서버로 보내지 않음
  2. Nginx (공유)도메인 이름으로 나눠, 한 컨테이너가 두 사이트의 HTTPS를 처리
  3. minunglee.cloudSpring Boot 앱으로 전달 (포트폴리오·게이트웨이)
  4. jipdon.com미리 빌드한 정적 파일을 바로 응답. 서버 프로그램이 없어 메모리를 거의 쓰지 않음
  5. jipdon.com/api실거래가 서버(Spring Boot)로 전달. IP당 초당 5회 제한
  6. 수집 배치6시간마다 국토부 API → PostgreSQL. 분석 결과는 Redis 캐시

세 저장소가 각자 독립적으로 배포합니다. PostgreSQL·Redis는 게이트웨이와 함께 쓰되 DB·계정·Redis 번호를 나눴고, 실거래가 서버는 힙 256MB·컨테이너 448MB로 제한합니다. Nginx는 API 주소를 요청 때마다 찾게 해 API가 꺼져 있어도 다른 사이트는 정상 동작합니다.

KEY DESIGN 핵심 설계 4가지

계산 로직 분리와 독립 검증

문제계산기는 한 번 틀리면 신뢰를 잃음. 화면 코드에 섞인 계산은 검증하기 어려움

계산을 화면과 분리한 순수 함수로 두고, 기대값은 손계산·고정밀 계산 등 코드와 독립된 방법으로 구해 대조. 반올림 자투리는 마지막 달에 정리해 잔액이 정확히 0이 되도록 함

추가 서버 비용 0원

문제사이트를 하나 늘릴 때마다 서버를 늘리면 비용이 계속 커짐

정적 사이트로 빌드해 기존 2GB 서버의 Nginx가 함께 서비스. 사이트별 설정 파일로 나눠 한 프로젝트의 배포가 다른 프로젝트 설정을 덮어쓰지 않게 함

링크 교체 방식 무중단 배포

문제파일을 덮어쓰는 도중에 접속하면 반쯤 바뀐 사이트가 보이고, 되돌리기도 어려움

새 버전을 커밋별 폴더에 올린 뒤 current 링크만 한 번에 바꿔 끼움. 최근 5개 버전을 남겨 링크만 바꾸면 즉시 롤백

바뀌는 기준값은 한 곳에서

문제기준금리·지수 수익률이 페이지 곳곳에 흩어지면 갱신을 빠뜨림

기준금리와 과거 수익률을 각각 데이터 파일 하나에 두고 확인 날짜·출처와 함께 화면에 표시. 숫자 한 줄만 고치면 모든 페이지에 반영

KEY DESIGN · SERVER 실거래가 서버 설계 4가지

멱등 수집

문제실거래가 자료에는 거래 고유 번호가 없고, 같은 달을 여러 번 다시 받아야 함 (늦은 신고·계약 해제)

거래 내용의 해시를 고유 키로 두고 INSERT … ON CONFLICT로 일괄 저장. 같은 달을 다시 받아도 줄이 늘지 않고, 계약 해제로 바뀐 매매는 해제 여부만 갱신

이어서 수집, 한도 안에서

문제83개 시군구 × 4종 × 24개월 ≈ 8천 번 호출. 공공 API는 하루 한도와 일시 오류가 있음

지역·종류·월 단위 수집 기록으로 할 일을 정하고, 최근 달부터 채움. 한 번에 3,000회까지, 한도 초과 응답이면 멈췄다가 다음 실행에서 이어 감. 일시 오류는 3번까지 재시도

흔들리지 않는 전세가율

문제급매·특이 거래 한두 건, 면적 표기 차이로 결과가 왜곡됨

평균 대신 중앙값, 전용면적은 소수점 버림으로 같은 타입끼리 비교. 최근 12개월에 거래가 없으면 24개월로 넓히고 쓴 기간·건수·근거 거래를 함께 보여줌

캐시 버전으로 일괄 무효화

문제새 거래가 들어오면 수만 건의 분석 캐시가 한꺼번에 낡음

캐시 키에 버전 번호를 넣고 수집 후 버전만 올림 — 키를 찾아 지우지 않음. 계산 방식 버전도 키에 넣어 배포 직후 예전 결과를 쓰지 않음. Redis 장애 시 캐시 없이 계산

TROUBLESHOOTING 만들며 겪은 문제

2026년 행정구역 개편으로 지역 코드가 바뀜

원인인천(중구·동구·서구)과 화성시가 새 구로 나뉘며 예전 코드로는 과거 거래까지 0건이 나옴

해결후보 코드 범위를 실제 API에 조회해 거래가 나오는 코드 8개를 찾고, 응답의 동 이름으로 어느 구인지 확인. 83개 지역 모두 실데이터로 검증

"등록되지 않은 서비스키" 오류

원인포털이 보여주는 키 중 이미 URL 인코딩된 키를 넣으면 호출할 때 한 번 더 인코딩됨

해결키에 %가 있으면 먼저 디코딩해 원래 값으로 맞춘 뒤 한 번만 인코딩. 어느 키를 넣어도 동작하게 하고 테스트로 고정

같은 타입이 두 면적으로 갈라짐 (운영 데이터에서 발견)

원인59.39㎡·59.97㎡처럼 신고된 같은 59㎡형이 반올림으로 59와 60으로 나뉘어 매매·전세 비교가 안 됨

해결소수점 버림("84㎡형" 표기와 같음)으로 변경하고, 캐시 키에 계산 방식 버전을 넣어 배포 즉시 반영

두 저장소가 하나의 Nginx 설정을 덮어씀

원인게이트웨이 배포가 설정 파일 전체를 올리는 구조라, 다른 사이트를 추가하면 다음 배포 때 지워짐

해결공통·게이트웨이·집돈 설정을 파일로 나누고 폴더째 읽게 변경. 각 저장소는 자기 파일만 올리고 nginx -t 검사 후 다시 읽기

컨테이너 안에서 배포 링크를 찾지 못할 수 있음

원인서버 경로(/home/deploy/sites)와 Nginx 컨테이너 안 경로(/var/www/sites)가 달라, 절대 경로 링크는 컨테이너에서 깨짐

해결current → releases/<커밋> 상대 경로 링크로 만들어 양쪽에서 같은 곳을 가리키게 함

모바일에서 페이지가 옆으로 94px 넘침

원인버튼처럼 꾸미려고 숨긴 라디오 입력이 입력칸 공통 스타일(너비 100%)을 받아 화면 밖까지 늘어남

해결숨긴 입력의 크기를 1px로 고정. 이후 모든 페이지를 375px 폭에서 가로 넘침 0인지 확인하는 절차를 추가

테스트가 실패했는데 틀린 건 테스트였음

원인자동차 할부 월 납입금 기대값을 어림으로 적어 둠 (724,691원)

해결40자리 정밀도로 따로 계산해 724,701.64원 → 코드(724,702원)가 맞음을 확인. 이후 기대값은 항상 독립 계산으로 구함

OPERATION 서비스로 운영하기
  • 검색 노출: 구글 서치콘솔·네이버 서치어드바이저 등록, sitemap(배포 시각 포함), 페이지별 구조화 데이터(JSON-LD), 공유 미리보기 이미지
  • 광고 준비: 소개·개인정보처리방침(광고 쿠키 고지)·이용약관·문의 페이지
