AI 비용 방어 게이트웨이

공개 AI 데모를 내 API 키로 운영해도, 비용이 하루 정해진 금액을 넘지 않고 봇과 장애로부터 안전하게 막아주는 서버

PROBLEM 왜 만들었나

누구나 쓸 수 있는 AI 체험을 공개하면, 호출 한 번 한 번이 내 API 키의 비용이 됩니다.

  • 비용 폭주: 누군가 스크립트로 반복 호출하면 하룻밤에 요금이 쌓인다
  • 동시 요청: "예산이 남았나?"를 확인하고 차감하는 사이에 여러 요청이 동시에 통과할 수 있다
  • 느린 외부 API: AI 응답을 기다리는 동안 서버 스레드가 묶여 다른 요청을 받지 못한다
  • 장애: 비용을 확인할 수 없는 상황에서도 호출이 나가면 통제가 무너진다

그래서 AI 호출 앞단에서 모든 요청을 확인하고, 비용을 미리 잡아두고, 실제 사용량으로 정산하는 게이트웨이를 만들었습니다.

ARCHITECTURE 요청 하나가 지나가는 길
  1. 봇 확인Cloudflare Turnstile 일회용 토큰을 서버에서 재확인실패 → 403
  2. 사용량 제한IP·초대코드별 시간당·하루 횟수를 Redis Lua 한 번으로 확인·차감초과 → 429
  3. 긴급 차단관리자 스위치가 켜져 있으면 AI를 부르지 않음→ 데모 응답
  4. 예산 선차감나올 수 있는 최대 비용을 하루 예산에서 먼저 확보부족 → 데모 응답
  5. Claude 호출Anthropic Java SDK, 가상 스레드에서 응답 대기실패 → 전액 반환
  6. 정산·기록실제 토큰 사용량으로 비용 계산, 차액 반환, PostgreSQL에 기록

Redis를 확인할 수 없으면 비용 통제가 보장되지 않으므로 AI를 호출하지 않습니다 (fail-closed).

KEY DESIGN 핵심 설계 5가지

Redis Lua로 원자적 사용량 제한

문제조회 → 계산 → 저장을 나눠 하면 동시 요청이 같은 값을 읽고 함께 통과

토큰 버킷과 하루 카운터를 Lua 스크립트 하나로 실행. Redis가 스크립트를 한 번에 처리해 중간에 끼어들 틈이 없음

최대 비용 선차감 → 실제 비용 정산

문제AI 응답이 오기 전에는 비용을 알 수 없음

최악의 비용을 먼저 잡고, 응답의 실제 토큰 수로 차액을 돌려줌. 요청이 몰려 칸이 일시적으로 차면 정산을 잠깐 기다려 재시도. 한도 초과 0건, 예산 활용 17.5% → 92%

가상 스레드로 느린 응답 대기

문제AI 응답 2초 동안 스레드 200개가 묶이면 처리량이 막힘

Java 21 가상 스레드로 대기 중 OS 스레드를 놓아줌. 동시 500명에서 처리량 2.1배, 응답 시간 절반

등급별 예산과 초대코드

문제게스트가 예산을 다 쓰면 면접관도 데모를 못 봄

게스트·초대코드 예산을 분리하고, 회사별 초대코드(서명 쿠키)로 더 좋은 모델과 넉넉한 한도 제공

다른 서비스가 쓰는 공통 AI 창구

문제두 번째 서비스(집돈)에 AI를 붙일 때 비용 방어를 또 만들면 중복

내부 API를 열어 집돈의 AI 계산기 안내가 이 게이트웨이를 거치게 함. 같은 단계를 거치되 서비스 몫의 등급·예산을 따로 둠. 바깥에서는 Nginx가 막고, 토큰이 틀리면 입력 검사보다 먼저 404

TROUBLESHOOTING 운영하며 겪은 문제

실제 Claude 첫 호출 직후 앱이 재시작됨

원인Metaspace 한도 128MB인데 Anthropic SDK 로딩 후 124MB 사용. 가짜 응답 부하 테스트로는 드러나지 않음

해결운영 로그에서 발견 → 로컬에서 실제 모드로 jcmd VM.metaspace 실측 → 한도 256MB

요청이 몰리면 예산의 18%만 쓰고도 "예산 소진"

원인최대 비용 선차감이 정산 전까지 예산 칸을 차지. 부하 테스트에서 1,000건 중 897건이 데모 응답

해결진행 중 선차감을 따로 집계해 "일시적으로 꽉 참"이면 정산을 최대 3초 기다림 + 답변 길이 512로 선차감액 절반 → AI 처리 103건 → 540건

서버를 재시작했더니 예전 버전이 뜸

원인배포 설정의 기본 이미지 태그 latest가 서버에 남은 예전 이미지를 가리킴

해결배포할 때 커밋 SHA를 서버 설정에 기록하고, 태그가 없으면 실행을 거부하도록 변경

IP를 바꿔 사용량 제한을 우회할 수 있음

원인클라이언트가 보낸 X-Forwarded-For를 Nginx가 그대로 이어붙임

해결Nginx에서 실제 접속 IP로 덮어쓰고, IP는 HMAC 해시로만 사용

배포는 성공인데 Nginx 다시 읽기·백업 등록이 안 됨

원인ssh로 보낸 배포 스크립트를 docker compose exec가 표준 입력으로 삼켜, 그 뒤 명령이 한 번도 실행되지 않음. 다른 저장소 배포가 Nginx를 다시 읽어 가려져 있었음

해결배포 후 서버에서 결과(crontab)를 직접 확인하다 발견 → exec에 < /dev/null. "초록불 = 성공"이 아니라 결과물을 확인
